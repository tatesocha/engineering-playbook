Case study 4 · Business problem

Give the answers live data, without opening a door to the machine.

A read-only queue lets a browser ask for facts. The machine that answers never accepts an incoming connection.

The problem, in one line. Agents answered from memory, and the machine that could fetch live data had no public address.

Why it matters. Fluent, stale answers are a business risk. Teams often reach for an open port to fix it, and that trades one risk for a worse one.

What we did

Runner

Polls out, never in

A background job on the machine asks the queue for work and posts answers back.

Tools

Read-only allow-list

Each agent sees only its own tools, and every tool is a read.

Auth

Fails closed

No token, a wrong token, or a missing header is refused.

Rules that come with it

  • No open port. The machine holds no tunnel and listens on nothing.
  • Requests expire. Queued requests and answers expire after ten minutes.
  • Names are checked. Every request is checked against fixed agent and tool names.

The trade-off, stated plainly

  • Polling adds a short delay to every answer.
  • An allow-list has to be maintained when a new tool is wanted.
  • The runner is one machine. If it sleeps, answers wait.
Why it matters, again. The queue gives the browser a way to ask, and gives nothing on the internet a way in.

Where else this shows up

  • Any internal tool that needs live data from a machine behind a firewall.
  • Decision: read-only first, with the allow-list and the token as the gate.
  • Owner: whoever runs the machine decides which tools it exposes.
